# 背景：问题现场

> 本文记录这个项目**为什么存在**。写于设计阶段（v0.1），内容来自真实工作场景的问题梳理与方案讨论。
> 保留「被否掉的方案」一节，是为了以后回头看时不必重走同样的弯路。

---

## 1 真实场景

不是理想化的实验室环境，而是有具体约束的生产现场：

| 环境 | 内容 |
|---|---|
| 网络 | **公司内网**，无外网依赖，服务需自建 |
| 代码所在 | 某个 **docker 容器**内（编码、编译） |
| 硬件所在 | **另一台 Windows 电脑**，上面连着一块 **FPGA 板子** |
| 团队 | 需要**同事协同**参与，但不是所有同事都该有权限 |

关键事实：**编码环境和目标硬件天然分离在两台机器上**。任何「一个进程编排全部」的方案在这里直接失效。

---

## 2 现有方案与它的失效点

现有做法是 `cannbot-skills` 仓的 `ops-direct-invoke` 插件——一套成熟的直调算子开发工作流：

- 一个 **PM 主 agent** 调度 6 类执行角色（architect / developer-code / developer-test / developer-doc / developer / qa）
- 8 个阶段、6 个用户确认点（CP0/CP1/CP2.2）
- 状态落盘 `.cannbot/<算子名>/state.json`，支持恢复
- 角色写权限由 `permissions/*.js` 机制约束

它设计得很好，但它建立在**进程内同步调用**这个前提上，于是：

| 失效点 | 后果 |
|---|---|
| subagent 不可人工干预 | 跑到硬件那一步出错，人只能等它失败；**调试体验极差** |
| 无法跨机器 | 连 FPGA 的环节根本没法放进同一个编排进程 |
| 回退复用原会话 | 会话销毁 / 上下文溢出后，返工所需的历史定位知识丢失 |
| 单写者假设失效 | 一旦多个执行者并行，`state.json` 会被互相覆盖 |

**注意**：这些失效点不是设计缺陷，而是**模式的上限**。工作流本身值得保留，要换的是它的执行载体。

## 3 需求清单

把每个 agent 提到独立 session 层级后，需要满足：

| # | 需求 |
|---|---|
| R1 | 每个 agent 是**独立 session**，用户可随时打开、对话、接管，不再是 subagent |
| R2 | agent 之间能**接力**：后一个能接上前一个的工作，而不是从零开始 |
| R3 | 存在一个**协作空间**，多个 agent（以及同事）可接入；**不在权限内的同事无法接入** |
| R4 | 能**派任务**给下游、能**广播**；接收方自主判断是否承接 |
| R5 | 协作空间本质是**普通文件系统**（人可直接查看、git 可管理），但**带 agent 间通信机制** |
| R6 | 空间内有 **AGENTS.md 类规范文档**做约束；每个 agent 可自由调用 skill 与 subagent |
| R7 | **人也能介入**：中途插话、改派、接管、回答确认点 |

其中 R5 是用户最初的直觉（"我希望协作空间就是一个普通文件系统"），它在讨论中被修正为：**文件系统只承担产物与长期记录，通信不能走文件**——理由见第 5 节。

### 3.1 需求变更与澄清（2026-10-29）

> **触发 A**：讨论「空间与网关是否一体、MCP 是否常驻、是否要在项目目录里固定配置」时，提出「**目录 = 成员资格**」（项目目录里放 `.space/tickets/*.ticket`，网关按 cwd 发现并自动 join、自动 attach）的方案。
> **结论 A**：用户否决——「用目录来区分成员，不太自由」。
>
> **触发 B**：追问「人能参与是什么意思」时，用户给出的是**会话级**的答案：打开 agent 自己的会话盯着它做、直接输入纠正。并指出 headless 后台模式做不到——但那是**调好之后才选的模式**。
>
> 本节只记**需求侧**的变更与澄清；**机制尚未选定，实现未动**，当前仍是 [ADR 0011](decisions/0011-gateway-connect-and-runtime-join.md) 的提示词 join 形态。

| 项 | 内容 |
|---|---|
| **新增需求 R8** | **身份与会话绑定，不与目录绑定**：任意目录里开的会话都可以是空间里任意一个合法成员；同一个目录里可以同时有多个不同身份的会话 |
| 推论 1 | 目录/项目级 MCP 配置只能表达「**这个目录允许连空间**」（能力开关：可入 git、不含秘密），**不能表达「我是谁」** |
| 推论 2 | 身份的交付必须是**会话级**的一步操作，不能依赖 cwd 结构与额外文件（目录发现方案见 §5.7） |
| 推论 3 | 「一人多目录」「一目录多角色」「临时换目录办事」三种情况都**不应要求改目录布局** |
| 代价 | 身份失去「所在目录」这个隐含边界，误接空间的成本变高 → 接入结果（空间名 + 成员名 + 角色）必须在工具返回里一眼可见 |

接入机制候选（**待定，本节不选型**）：

| 候选 | 形态 | 待评估 |
|---|---|---|
| a | 提示词 `space_join(url, token)` | 已验证可用；url + token 要人抄，且进会话历史 |
| b | 凭据库 + 会话启动自动 join（`space login`） | 凭据存哪、能否跨机器同步 |
| c | 会话级注入：环境变量 / runtime 启动参数带 ticket | 不进对话历史，但每会话要配一次 |
| d | launcher `space session -- <runtime> ...` 包住启动 | 跨 runtime 统一，代价是多一层进程 |

#### R7 的细化：人对 agent 的干预分两条通道

「可人工干预」（R7）此前只写在需求里，没有落到机制。澄清后它是一条**分通道**的需求：

| 通道 | 做法 | 前置条件 | 生效时机 | 适用 |
|---|---|---|---|---|
| **① 会话内（主通道）** | 人打开那个 agent **自己的**会话（TUI / GUI），直接输入纠正 | 该会话是**可被前端打开**的交互会话；`headless` 不成立 | **立刻**（打断在飞 turn） | 人在旁边、要盯着干 |
| **② 空间内（兜底）** | 人用自己的 `human` 会话发消息 / 收回任务 | 无需人在运行时旁边 | 下一次 `wait` 返回，或下一个工具调用边界 | 跨机器、无终端、人不在旁边 |

- **默认形态是交互会话**；`headless`（D 档）是「agent 已经调得比较好」之后的选择，**明确放弃实时盯人这个能力**，不把它视为缺陷。
- 拆解「打断」这个词在协议里的边界：**空间推不动一个正在生成的 turn**；②只在工具调用边界生效；**硬停止 = 关掉会话**（runtime 能力，不是空间能力）。
- 服务端已为通道 ① 预埋：`notifications/cancelled` 中止在飞的 `wait` handler（`src/space/mcp.mjs`）、`wait` 一发现 abort 就收手（`src/space/service.mjs`），验收里「人插话后恢复等待」已绿。
- **P7/P8 已实测**（[probe/RESULTS.md](../probe/RESULTS.md)）：opencode `abort` 与 dsh `SIGINT` 都会把 cancellation 传到在飞的 MCP 工具调用（41ms / ~230ms）；
  **但直接输入不会打断**——opencode 把新消息排队到 turn 之后。所以人动作的口径是「**先停，再输入**」。
- **审计归属**：人替成员代打时，空间事件记在**该成员**名下，不是 human。倾向把权威动作（放宽硬门槛 `relax`、收回任务）保留在**人自己的 human 会话**里做，日常纠正走键盘——这条待确认。

不随本次变更改动的既有结论（来自上一轮讨论，仍成立）：

- **hub 常驻、网关每会话**——两者生命期不同、跨机器时数量不同，不能合并进程；「一体」只能落在命令层（`space up` 产出凭据，成员侧一条命令接入）。
- **网关可以常驻与否是状态问题，不是进程问题**：真正需要 daemon 的只有「跨会话保留 joined 状态与凭据」这一条诉求。
- **身份属于会话（Q1 = ii）**：同一目录可并存多个不同身份的会话；「人下场干活」= 换一个角色身份的会话，不给 human 角色特权（唯一例外是既有的 `relax` 与拟议的「收回任务」）。
- **本机与服务器同一套流程（Q2）**：本机用回环地址，差别只有「谁常驻」。

#### 已验证：P7/P8/P9 探针（2026-10-30）

| # | 假设 | 结果 | 证据 |
|---|---|---|---|
| **P7** | 人**停止**当前 turn → 在飞的 MCP 工具调用收到 `notifications/cancelled` | ✅ opencode（`/abort`，41ms）· ✅ dsh（SIGINT，~230ms） | `probe/results/raw/p7.{opencode,dsh}.stop.*` |
| **P8** | 人**直接输入新消息**（不按停止）会打断在飞工具调用 | ❌ opencode：20s 内无 cancelled，消息排队；dsh GUI 未测 | `probe/results/raw/p7.opencode.type.*` |
| **P9** | 同一会话能被**第二个前端**挂上看并输入 | ✅ opencode `attach -s <session>` / `web`；⚠️ DSH GUI 可开自己的会话，`headless` 不行 | `p7-interrupt.mjs` 头注释 + `opencode attach --help` |

**用法口径（通道 ① 成立的前提）**：人看到 agent 做错了 → **先停止当前 turn，再输入纠正**。
直接打字在 opencode 上只是排队，agent 仍会把当前工具调用跑完（可能是几分钟的 `wait`）。
DSH GUI 的停止按钮是否与 SIGINT 同一条 abort 路径，仍需人工确认（列入 P8 待测）。

按 AGENTS.md 原则 4（探针先于实现），通道 ① 的实现（以及用法文档）以本表为准。

**追加实测（2026-10-31，见 [probe/RESULTS.md](../probe/RESULTS.md) P10–P12）**：

- opencode 上「推」可行：插件在 `session.idle` 注入消息会开新 turn → agent 可以真正空闲，由插件在有活时叫醒。
  代价是**每次唤醒 = 一次完整模型 turn**，所以只适合低频兜底，`wait` 仍是主循环。
- DSH 侧 Stop hook 本机无法实测（hooks bridge 0.1.2 与 dsh 0.2.1 版本不配套），待配套再验。
- 「会话结束释放租约」已落实现：`space_detach` 现在会收回该成员持有的任务（回 PENDING、改派到角色、不算失败），
  网关进程退出时自动 detach——崩溃检测因此不再依赖 900s 租约过期。

## 4 关键约束（不可协商）

| 约束 | 影响 |
|---|---|
| **环境异构** | docker/Linux + Windows 三处以上，必须跨进程跨机器 |
| **agent 离线是常态** | agent 是「用户启动的 session」，不是常驻服务；中心**推不动**它 |
| **不追求跨组织互通** | v0 只服务自有 agent，互操作是后续能力 |
| **大文件必须能交接** | 要把大文件交给同事，git 管不住；需内容寻址 + 引用 |
| **成本会失控** | 无人值守 + 多 agent + 长任务 = 需要预算熔断 |

## 5 被否掉的方案（避免重走）

讨论中逐条评估并否决的方案，附否决理由：

### 5.1 纯文件系统当协作空间（最初构想）

**否决理由**：文件数量会爆炸。每个消息、每次心跳、每条状态变更都落一个文件，几天就不可维护。而且 SMB/NFS 上文件锁与 `inotify` 语义都不可靠，跨机器竞态无法保证。

**修正**：文件系统降级为**只承载产物与长期记录**；通信和状态走中心服务。

### 5.2 用 hook 作为「挂到协作空间」的机制

**否决理由**：hook 是**无状态事件回调**，无法承载身份与租约；且不同 runtime 的 hook 能力差异极大（部分 CLI 完全没有项目级 hook）。把入场建在 hook 上，等于换个 CLI 就用不了。

**修正**：入场用显式 `attach`（MCP 接入），hook 只做**围栏**（越权写拦截、会话结束释放租约），不做**大门**。

### 5.3 直接采用 A2A 协议作为空间

**否决理由**：A2A 是**点对点**协议，房间 / 成员 / ACL / 广播 / 共享黑板**全部「协议未定义」**，且与其「agent 是 opaque 的」原则直接冲突——它缺的正好是我们要的。另外版本半年内两次结构级变动，现在压核心等于提前买重构成本。

**修正**：**借用它的数据模型（TaskState 分类、Task Immutability、contextId、tenant 字段），不实现它的协议**。详见 [decisions/0003](decisions/0003-borrow-a2a-vocabulary-not-adopt.md)。

### 5.4 直接用 git 仓当协作空间

**否决理由**：权限边界（分支保护 / CODEOWNERS）确实很强，历史与 diff 也很好，但**并发写会冲突**，且**大二进制不适合入 git**（LFS 在内网麻烦）。

**修正**：git 保留为**文本产物的版本载体**，不作为通信介质，也不承载大文件（大文件走 NAS/对象存储 + 引用）。

### 5.5 通过注入 stdin / tmux 唤醒交互式会话

**否决理由**：交互式 CLI 的 turn 由输入事件驱动，没人打字就没有 turn。强行注入**跨 runtime 完全不通用**且脆弱，属于 hack 而非机制。

**修正**：改问「它在线时怎么知道自己该干活」——由 agent 自己在 turn 里调用 `wait` 阻塞等待。见 [decisions/0004](decisions/0004-wakeup-model-wait-first.md)。

### 5.6 把 subagent 全部替换成 peer agent

**否决理由**：会同时丢掉 subagent 的核心优势——上下文天然共享、同步、原子。代价是**上下文丢失成为头号故障源**（下游拿到产物却不知道上游为什么这样决策，于是重做一遍）。

**修正**：**peer 与 subagent 是两个正交维度**，按「人有没有可能在中间插手」分层。见 [protocol §1.3](design/protocol-v0.1.md)。

### 5.7 「目录 = 成员资格」（`.space/tickets/*.ticket` + 网关按 cwd 发现）

**否决理由**：成员是**会话 / 人**，不是目录。把「我是谁」交给目录布局，等于把身份绑在文件系统结构上：

- 同一个仓库里同时开 pm 与 dev 两个会话（一个评审、一个改代码）是常态，一个目录只能放一个默认身份
- 一个人要在多个项目目录里以同一身份工作，得给每个目录各塞一份凭据
- 临时在别的目录开会话办事（看日志、跑脚本），拿不到身份
- 凭据落进项目目录，和「配置可提交、秘密不可提交」的分裂也更脆

**保留的正确部分**：**目录/项目级 MCP 配置这件事本身是对的**——它解决的是「哪些目录能接空间」（工具面 opt-in、配置不含秘密、可入 git），只是**不能兼任身份**。这两件事必须拆开，见 §3.1 R8。

---

## 6 一句话总结

> 要保留的是 `ops-direct-invoke` 的**流程与状态机**；要换掉的是它的**执行载体**——从进程内调用改成跨机器、可离线、可人工干预的消息协作，并让**文件系统退回到它真正擅长的事**：存产物。
