# 背景：问题现场

> 本文记录这个项目**为什么存在**。写于设计阶段（v0.1），内容来自真实工作场景的问题梳理与方案讨论。
> 保留「被否掉的方案」一节，是为了以后回头看时不必重走同样的弯路。

---

## 1 真实场景

不是理想化的实验室环境，而是有具体约束的生产现场：

| 环境 | 内容 |
|---|---|
| 网络 | **公司内网**，无外网依赖，服务需自建 |
| 代码所在 | 某个 **docker 容器**内（编码、编译） |
| 硬件所在 | **另一台 Windows 电脑**，上面连着一块 **FPGA 板子** |
| 团队 | 需要**同事协同**参与，但不是所有同事都该有权限 |

关键事实：**编码环境和目标硬件天然分离在两台机器上**。任何「一个进程编排全部」的方案在这里直接失效。

---

## 2 现有方案与它的失效点

现有做法是 `cannbot-skills` 仓的 `ops-direct-invoke` 插件——一套成熟的直调算子开发工作流：

- 一个 **PM 主 agent** 调度 6 类执行角色（architect / developer-code / developer-test / developer-doc / developer / qa）
- 8 个阶段、6 个用户确认点（CP0/CP1/CP2.2）
- 状态落盘 `.cannbot/<算子名>/state.json`，支持恢复
- 角色写权限由 `permissions/*.js` 机制约束

它设计得很好，但它建立在**进程内同步调用**这个前提上，于是：

| 失效点 | 后果 |
|---|---|
| subagent 不可人工干预 | 跑到硬件那一步出错，人只能等它失败；**调试体验极差** |
| 无法跨机器 | 连 FPGA 的环节根本没法放进同一个编排进程 |
| 回退复用原会话 | 会话销毁 / 上下文溢出后，返工所需的历史定位知识丢失 |
| 单写者假设失效 | 一旦多个执行者并行，`state.json` 会被互相覆盖 |

**注意**：这些失效点不是设计缺陷，而是**模式的上限**。工作流本身值得保留，要换的是它的执行载体。

## 3 需求清单

把每个 agent 提到独立 session 层级后，需要满足：

| # | 需求 |
|---|---|
| R1 | 每个 agent 是**独立 session**，用户可随时打开、对话、接管，不再是 subagent |
| R2 | agent 之间能**接力**：后一个能接上前一个的工作，而不是从零开始 |
| R3 | 存在一个**协作空间**，多个 agent（以及同事）可接入；**不在权限内的同事无法接入** |
| R4 | 能**派任务**给下游、能**广播**；接收方自主判断是否承接 |
| R5 | 协作空间本质是**普通文件系统**（人可直接查看、git 可管理），但**带 agent 间通信机制** |
| R6 | 空间内有 **AGENTS.md 类规范文档**做约束；每个 agent 可自由调用 skill 与 subagent |
| R7 | **人也能介入**：中途插话、改派、接管、回答确认点 |

其中 R5 是用户最初的直觉（"我希望协作空间就是一个普通文件系统"），它在讨论中被修正为：**文件系统只承担产物与长期记录，通信不能走文件**——理由见第 5 节。

---

## 4 关键约束（不可协商）

| 约束 | 影响 |
|---|---|
| **环境异构** | docker/Linux + Windows 三处以上，必须跨进程跨机器 |
| **agent 离线是常态** | agent 是「用户启动的 session」，不是常驻服务；中心**推不动**它 |
| **不追求跨组织互通** | v0 只服务自有 agent，互操作是后续能力 |
| **大文件必须能交接** | 要把大文件交给同事，git 管不住；需内容寻址 + 引用 |
| **成本会失控** | 无人值守 + 多 agent + 长任务 = 需要预算熔断 |

## 5 被否掉的方案（避免重走）

讨论中逐条评估并否决的方案，附否决理由：

### 5.1 纯文件系统当协作空间（最初构想）

**否决理由**：文件数量会爆炸。每个消息、每次心跳、每条状态变更都落一个文件，几天就不可维护。而且 SMB/NFS 上文件锁与 `inotify` 语义都不可靠，跨机器竞态无法保证。

**修正**：文件系统降级为**只承载产物与长期记录**；通信和状态走中心服务。

### 5.2 用 hook 作为「挂到协作空间」的机制

**否决理由**：hook 是**无状态事件回调**，无法承载身份与租约；且不同 runtime 的 hook 能力差异极大（部分 CLI 完全没有项目级 hook）。把入场建在 hook 上，等于换个 CLI 就用不了。

**修正**：入场用显式 `attach`（MCP 接入），hook 只做**围栏**（越权写拦截、会话结束释放租约），不做**大门**。

### 5.3 直接采用 A2A 协议作为空间

**否决理由**：A2A 是**点对点**协议，房间 / 成员 / ACL / 广播 / 共享黑板**全部「协议未定义」**，且与其「agent 是 opaque 的」原则直接冲突——它缺的正好是我们要的。另外版本半年内两次结构级变动，现在压核心等于提前买重构成本。

**修正**：**借用它的数据模型（TaskState 分类、Task Immutability、contextId、tenant 字段），不实现它的协议**。详见 [decisions/0003](decisions/0003-borrow-a2a-vocabulary-not-adopt.md)。

### 5.4 直接用 git 仓当协作空间

**否决理由**：权限边界（分支保护 / CODEOWNERS）确实很强，历史与 diff 也很好，但**并发写会冲突**，且**大二进制不适合入 git**（LFS 在内网麻烦）。

**修正**：git 保留为**文本产物的版本载体**，不作为通信介质，也不承载大文件（大文件走 NAS/对象存储 + 引用）。

### 5.5 通过注入 stdin / tmux 唤醒交互式会话

**否决理由**：交互式 CLI 的 turn 由输入事件驱动，没人打字就没有 turn。强行注入**跨 runtime 完全不通用**且脆弱，属于 hack 而非机制。

**修正**：改问「它在线时怎么知道自己该干活」——由 agent 自己在 turn 里调用 `wait` 阻塞等待。见 [decisions/0004](decisions/0004-wakeup-model-wait-first.md)。

### 5.6 把 subagent 全部替换成 peer agent

**否决理由**：会同时丢掉 subagent 的核心优势——上下文天然共享、同步、原子。代价是**上下文丢失成为头号故障源**（下游拿到产物却不知道上游为什么这样决策，于是重做一遍）。

**修正**：**peer 与 subagent 是两个正交维度**，按「人有没有可能在中间插手」分层。见 [protocol §1.3](design/protocol-v0.1.md)。

---

## 6 一句话总结

> 要保留的是 `ops-direct-invoke` 的**流程与状态机**；要换掉的是它的**执行载体**——从进程内调用改成跨机器、可离线、可人工干预的消息协作，并让**文件系统退回到它真正擅长的事**：存产物。
