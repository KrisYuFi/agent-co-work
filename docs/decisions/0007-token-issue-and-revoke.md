# 0007. token 签发与吊销：CLI 签发、库内只存哈希

- **状态**：已接受
- **日期**：2026-10-28
- **影响面**：安全入口 / 接入流程（协议 §2.2）
- **结案**：协议 §13 未定项 #3（「token 发放 / 吊销的操作流程」），原定「阶段 2 前」定，按时定

## 背景

协议 §2.2 只写了「token 由空间管理员发放，绑定 `member_id` + `role` + `scopes[]` + 有效期，支持吊销」，**没写怎么发**。这是安全入口：它决定了「权限外的同事到底能不能接进来」，不能留到实现时随手决定。

硬约束：

- 环境是**公司内网、无外网**，不能假设有 OIDC / SSO 可用
- **权威边界必须在 server**（§2.2）：不能在共享目录里放权限配置文件，那只能防误操作
- 阶段 2 要能跑「拿另一个 token attach，验证越权被拒绝」这条验收项

## 决策

1. **签发走 CLI，不走 MCP**：`space token issue --member dev-hw --role developer --kind role --scopes task,publish,msg --ttl 7d`
   - 能在本机跑 CLI 并读到库文件 = 管理员身份。**不做单独的 admin token**——那会引入「管 token 的 token」这层自举问题。
2. **库内只存哈希**：`tokens` 表存 `sha256(token)`（`token_hash` 主键）+ `prefix`（前 8 字符，供人肉核对）+ 绑定信息 + 有效期 + 吊销时间。**明文 token 只出现一次**（签发时打印），服务端永不落明文。
3. **令牌形态**：`spt_<32 hex>`，无结构、不签名。吊销靠查库，不靠自包含声明。
4. **使用方式**：`space serve --token-file <path>` 或 `SPACE_TOKEN` 环境变量。`attach` 时校验，失败返回 `TOKEN_INVALID` / `TOKEN_REVOKED`。
5. **吊销语义**：`space token revoke --member <id>` → 置 `revoked_at`，并在**同一事务**里：
   - 该成员名下 `PENDING` 任务保持原样（别人可认领）
   - 该成员持有的 `CLAIMED` / `WORKING` 任务**回 `PENDING` 并释放租约**（§2.2「吊销后已发出的 task 自动回 PENDING」）
   - 记 `member.detached` + `token.revoked` 事件
6. **有效期到期**按同一路径处理（复用吊销逻辑，不写第二套）。

## 后果

**正面**

- 权限边界完全在库与事务里，**没有「放在共享目录的权限文件」这个漏洞面**
- 泄露代价可控：`prefix` 只能用于人工核对，库泄露也拿不到可用 token
- 吊销即时生效且**带状态回收**——这点比多数原型方案（只让 token 失效、任务卡死在别人名下）更接近真实

**负面 / 代价**

- **没有刷新与轮转**：TTL 到期就必须重发，长任务中间会被踢。v0 用「发长 TTL」糊过去，属已知缺口
- **没有审计签名**：签发/吊销只落普通事件，可被任何能改库的人改写。**本机 sqlite 就是信任边界**
- **token 走命令行参数会进 shell history**（`--token` 直接传）；文档要求用 `--token-file` 或环境变量
- 没有「多设备/多会话」的 token 区分：一个成员一个 token，一台机器泄露等于整个角色泄露

## 备选方案

| 方案 | 放弃理由 |
|---|---|
| JWT / PASETO 自包含 | 需要密钥管理 + 吊销名单（等价于再建一张表），换来的「无状态校验」在这个规模没有价值 |
| 共享目录放 `permissions/*.json` | 正是 §2.2 明确否掉的做法：防误操作不防越权 |
| 每人手工往 sqlite 里插行 | 无哈希、无前缀、易错，且把「怎么发」变成口口相传 |
| 走 MCP 工具 `space_token_issue` | 需要先有可信身份才能签发 → 自举。且会把这套能力暴露给所有已接入成员 |
| 复用现有 SSO / OIDC | 内网无外网，且本项目刻意不依赖组织基础设施（跨组织留到阶段 5 评估 AGNTCY） |
