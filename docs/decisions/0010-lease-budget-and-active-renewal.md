# 0010. 租约预算与「活跃即心跳」

- **状态**：已接受
- **日期**：2026-10-28
- **影响面**：协议 §4.2 / §6.2 / §12；`src/space/service.mjs`、`src/space/mcp.mjs`
- **来源**：多机形态实跑中撞到的真实故障

## 背景

多机跑设计段时，QA 复核一份 30KB 的《开发方案》花了 5 分钟出头。租约是 300s，于是：

```
07:29:08  task.claimed   [CP2.2] @qa          ← 认领
07:29:08  task.transitioned CLAIMED→WORKING
07:34:05  task.expired   [CP2.2] WORKING→PENDING attempts=1   ← 租约过期，任务被回队
07:34:30  artifact.published [CP2.2] @qa      ← 它其实还在干活
07:34:50  task.claimed   [CP2.2] @qa          ← 自己重新认领
07:34:57  task.transitioned WORKING→DONE
```

这次它自愈了（QA 恰好自己又认领回来）。但**换个场景就是两个成员同时干同一件事**：
任务回队后，另一个空闲成员会认领它，而原来的成员还在写报告。

根因不是「租约太短」这么简单，而是这条假设：

> 租约靠**周期性心跳**维持。

这条假设对常驻服务成立，对 LLM agent **不成立**——一个 agent 在「写一份 30KB 的文档」这种
长 turn 里可以几分钟不调用任何工具，期间没有任何信号。而它并没有掉线。

## 决策

**三条，全部落在机制里：**

1. **「活跃即心跳」**：成员**任何一次工具调用**都会顺延它当前持有的任务租约（`touchMemberLeases`）。
   agent 不需要记得调 `space_task_heartbeat`——它只要还在用空间，就说明它还活着。
2. **默认租约 300s → 900s**：实测一次设计复核 5 分钟出头，300s 不够。
   `claim` 仍可用 `lease_sec` 指定（测试与快任务用短租约，上限仍是 3600s）。
3. **过期只由第三方触发**：持有者自己的调用是**续期**，不是检查。所以「任务过期」这件事
   只会在**别的成员操作、或新成员接入**时被发现。

## 后果

**正面**

- 「干活期间不心跳 → 任务被抢」这个故障面消失，而且**不依赖 agent 自觉**
- 崩溃检测仍然成立：成员真的掉线后，它的租约不再被任何人续期，别人一操作就会扫到
- 短租约的能力保留（测试、快任务），不必为长任务牺牲回收速度

**负面 / 代价**

- **崩溃检测变慢**：默认从 30s 级变成 15 分钟级（900s + 下一次扫描）。对一个「agent 离线是常态」
  的系统，这个延迟是要付的代价——目前靠 `lease_sec` 按任务类型调，阶段 4 引入 D 档（server 拉起执行）
  时应按下发时的任务类型给不同预算
- 「活跃」的判定粒度是「最近一次工具调用」，不是「进程还活着」。一个**卡在模型调用里**的 agent
  同样会掉租约——这是和上面同一条限制的另一面
- 每次工具调用多一次 `count` 查询（无租约时不开写事务），有租约时多一个 UPDATE 事务

## 备选方案

| 方案 | 放弃理由 |
|---|---|
| 让 agent 在 prompt 里记得定期 `heartbeat` | 这正是「把机制写进提示词」，AGENTS.md 原则 3 的反例；模型会忘 |
| 租约无限长 | 失去崩溃回收，ROADMAP 阶段 4「杀掉任意成员任务自动回队」直接失效 |
| 成员侧桥接进程自动心跳（stdio） | stdio 可行（有常驻进程），但 **HTTP 无连接态**做不到，而跨机器正是走 HTTP |
| 按心跳频率动态算租约（服务端统计调用间隔） | 需要先有历史数据；原型阶段先用「活跃即续期 + 长默认值」这组简单规则 |
