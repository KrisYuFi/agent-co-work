# 0012. 多空间：一个会话同时连几个空间，工具带 `space` 别名

- **状态**：已接受（待实现）
- **日期**：2026-10-28
- **影响面**：网关侧工具形状（ADR 0011 的延伸）、成员侧 UX
- **前置**：[ADR 0011](0011-gateway-connect-and-runtime-join.md)（网关 `space connect` + 运行时 join）

## 背景

ADR 0011 的网关按「一个会话连一个空间」设计。但这对人的直觉不成立：

> 人也经常在各种群里找信息。

架构师的会话可能需要同时待在「某个算子的空间」和「团队公共空间」；PM 可能同时盯着两条流水线。
把它们合成一个空间是错的（权限与噪声都不同），强迫开两个会话也是错的（人只有一个脑子）。

所以网关要支持**多空间并存**，问题随之而来：**每次工具调用要发给哪个空间？**

## 决策

**一、`space_join` 带别名，空间以别名标识**

```
space_join({ space: "work",  url: "http://hub-a:7321/mcp", token: "spt_…" })
space_join({ space: "team",  url: "http://hub-b:7321/mcp", token: "spt_…" })
space_leave({ space: "team" })
space_spaces()  → [{space:"work", hub:"…"}, {space:"team", hub:"…"}]
```

别名由**调用方**起（通常是「这个空间在你这儿叫什么」），不要求与 hub 的库名一致。

**二、每个工具多一个可选入参 `space`**

- `space` 省略且**只连了一个**空间 → 用它（最常用的情形，零负担）
- `space` 省略且**连了多个** → 拒绝（`AMBIGUOUS_SPACE`），不做猜测。猜错会把消息发到错误的群体里
- `space` 指定 → 路由到该别名

**选这条路而不是「工具按空间加前缀」**（如 `work__space_attach`）的理由：
前缀会让工具名随 join/leave 变化，agent 的上下文里工具清单要跟着刷新（`list_changed`），
而且模型容易把前缀写错。多一个可选参数是**模型最熟的形状**，也不改变工具集的数量。

**三、`space_attach` 仍然是**每个空间各报一次到**

join 只是连接；每个空间要各自 `space_attach`（各自上报宪法版本与 capabilities）。
身份也是每个空间一份 token —— 你可以在 A 空间是 architect，在 B 空间是 reviewer。

## 后果

**正面**

- 一个会话能同时待在多个空间，符合人的直觉（多群并存）
- 状态隔离清楚：同一个 `space` 别名内的 task_id、租约、游标互不串台
- 不改变 hub 的任何工具定义（`space` 参数只存在于网关层）

**负面 / 代价**

- 每个工具多一个参数，schema 变长；模型偶尔会漏传（只连一个空间时不影响，多空间时会收到 `AMBIGUOUS_SPACE` 并自我纠正）
- 别名由调用方起，两个人对同一个空间可能起不同别名 —— 目前只影响会话内可读性，不做统一
- 快照式状态（joined 列表）在网关进程内存里，网关重启即丢，需要重新 join
- 跨空间的 task_id 可能看起来相似（`t_xxxxxxxx`），排障时必须带空间名读 trace

## 备选方案

| 方案 | 放弃理由 |
|---|---|
| 一个会话只连一个空间，多空间开多会话 | 与「人只有一个脑子」冲突；而且多开会话要多份配置、多份 token |
| 工具按空间加前缀（`work__space_attach`） | 工具集随 join/leave 动态变化，需要 `list_changed`；模型写前缀易错 |
| 全局「当前空间」切换（`use space work`） | 隐式状态：一次忘记切换就把消息发错群体，且难以回溯。显式 `space` 参数更符合「机制优于自然语言」 |
| 把多个空间合并成一个 hub 的多 space | 权限与噪声无法隔离；跨机器时也不现实（不同 hub 在不同服务器） |
