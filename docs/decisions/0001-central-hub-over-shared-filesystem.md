# 0001. 用中心服务做协作总线，而非共享文件系统

- **状态**：已接受
- **日期**：2026-10-28
- **影响面**：整体架构 / 存储 / 并发模型 / 权限模型

## 背景

最初的构想（也是最自然的构想）是：**协作空间就是一个普通文件系统**，每个 agent 读写文件来协作——发布产物写文件、派任务写文件、状态更新写文件。好处直白：人可以直接用 `ls` 看、用 git 管版本、不需要部署任何服务、单机就用本地目录。

公司内网环境、多台异构机器（docker 容器 + Windows + FPGA）的现场，让这个方案格外诱人：共享文件夹看起来是唯一一个所有机器都能访问的东西。

但评估后发现四个无法绕开的问题：

1. **文件数量爆炸**。消息、心跳、状态变更、认领记录，如果每条都落一个文件，几天内目录就不可维护；若再进 git，仓会迅速失去意义。
2. **并发竞态无法保证**。认领要用近似原子操作硬撑（如 `mkdir`），而 **SMB/NFS 上的文件锁与 `inotify` 语义都不可靠**——跨机器时「文件监听到变化就干活」在关键时刻会失效。
3. **跨机分布式难题全部要自己写**：租约、心跳、任务重投、死会话检测、资源互斥。每一件都很难写对。
4. **权限做不真**。能写共享文件夹的人就能改配置文件，空间内的「权限配置」只能防误操作，防不了越权。

同时现场存在一个天然事实：**连 FPGA 的机器本来就只有一台**。跨机器不是普遍需求，而是一个可控的集中点。

## 决策

引入**一个中心协作空间服务**（单进程 + 单 sqlite），所有成员通过它协作。文件系统**降级为只承载产物与长期记录**，不承担通信与状态。

- 单机场景：`--listen 127.0.0.1`，一份实现即可
- 团队场景：`--listen 0.0.0.0`，内网服务器，同一份代码

## 后果

**正面**

- 上面四个问题全部消失：原子认领 = 一条事务；死会话检测 = 连接断开即知；任务重投 = 队列 TTL；**FPGA 互斥 = 一行唯一约束**；权限 = 服务端鉴权（从"做不到"变成"很好做"）
- 集中化产生一个**免费的关键副产品**：服务端有一条完整的消息与任务流水线，天然就是**调试 trace**。这正好解决项目最初的痛点「subagent 不好调试」
- 单机与团队同一套实现，不会演变成两套系统

**负面 / 代价**

- **引入单点**：服务挂了所有 agent 停下。对单机场景无成本；对内网服务器必须接受（人类论坛/邮件列表也如此）
- **需要部署与运维**：比"丢一个共享文件夹"麻烦
- **agent 离线后无法被推送**（架构层面）→ 必须设计离线队列与唤醒机制（见 ADR 0004）
- 人不能再用 `ls` 直接看到通信过程 → 必须提供等价的观察界面

## 备选方案

| 方案 | 放弃理由 |
|---|---|
| 共享文件系统 + 文件约定 | 文件爆炸、跨机锁不可靠、分布式难题自建、权限做不真 |
| git 仓当空间 | 权限与历史确实很好，但**并发写冲突**且**大二进制不适合入 git**（LFS 在内网麻烦） |
| 纯 P2P（每个 agent 互联，无中心） | 成员发现、广播、成员表、权限全要自建；本场景不追求跨组织去中心化，成本收益不划算 |
| 直接用 A2A（点对点） | 见 ADR 0003：它不提供空间语义 |

## 备注

文件系统并没有被抛弃——它在**该用的地方**继续发挥作用：产物、大文件、handoff 文档、长期记录。本 ADR 否掉的是"**用文件系统做通信介质**"，不是"用文件系统存东西"。
