# 0005. `wait` 单次阻塞时长以 20s 为默认，且须由客户端声明上限

- **状态**：已接受
- **日期**：2026-10-28
- **影响面**：协议（§6 唤醒模型 / §7 接口 / §11 错误码）/ 接入层 / 空间宪法
- **来源**：阶段 1 技术探针实测，见 [`probe/RESULTS.md`](../../probe/RESULTS.md)

## 背景

ADR 0004 把 `wait` 长轮询定为主唤醒路径，并把成立性押在一个外部事实上：**agent 能在自己的一个 turn 里调用阻塞工具而不被打断**。阶段 1 实测（opencode 1.18.23 / DSH 0.1.2-rc.1）给出的答案是「成立，但有条件」：

| 事实 | 实测值 |
|---|---|
| 调高客户端 MCP 工具调用超时后，单次阻塞 | opencode ✅ 150s · DSH ✅ 150s（服务器侧实际阻塞 150.0s） |
| 客户端默认 MCP 工具调用超时 | opencode **30s** · DSH **60s** |
| 默认配置下阻塞 90s | 两边都断：`MCP error -32001` / `Request timed out`，**服务器还在跑，客户端先放弃** |
| 打断来源 | **工具调用超时**，不是 turn 超时（内置 `sleep 150` 在两边都完整跑完） |
| 进度通知能否续期 | opencode ✅（`resetTimeoutOnProgress`，10 条进度撑住 150s）· DSH ❌（**根本不带 `progressToken`**） |

关键结构性事实：**这个超时是客户端侧配置，服务端既看不见也强制不了。** 也就是说，一个「按 5 分钟设计」的 `wait` 在默认配置的客户端上必然失败——而且失败形态是**静默的错误路径**：agent 拿到一个超时错误，看起来像空间服务坏了，实际是它自己配错了。

这属于「半年后有人会问为什么当初不那样做」的决策点，因此单独记一条。

## 决策

**四条，全部落进机制，不落进提示词：**

1. **`space_wait` 的默认单次阻塞时长 = 20s**，不是 60s、不是 300s。取 20s 是因为它低于**已知最小默认值**（opencode 30s），留一次往返余量。语义不变：`wait` 本来就带 `since_cursor`，超时返回后循环再调。
2. **`space_attach` 的 `capabilities[]` 增加 `max_block_sec`（客户端自报单次能挂多久）**。`space_wait` 接受 `timeout_sec`，**server 将其 clamp 到该成员的 `max_block_sec`**，并在返回值里回显生效值 `effective_timeout_sec`。未声明时按 20s 处理，不报错。
3. **`wait` 超时返回是正常返回，不是错误**。返回值标注 `reason: "timeout"`，agent 必须继续循环。协议层面不允许客户端把超时当失败处理——否则 agent 会「礼貌地」放弃等待。
4. **进度通知只作可选优化，不作正确性依赖**。server 可在 `wait` 期间发 `notifications/progress`（对 opencode 这类支持续期的客户端有用），但**不得**假设它能延长任何客户端的超时。

配套的**接入前置条件**（写进空间宪法，因为服务端校验不了客户端进程的启动参数）：

> attach 前，客户端的 MCP 工具调用超时必须配置为 ≥ `2 × max_block_sec`。
> opencode：`mcp.<name>.timeout`（默认 30000）
> DSH：`@deepseek-ai/dsh-mcp-client` 的 `toolCallTimeoutMs`（默认 60000）

这条之所以留在宪法而不是机制里：**它是客户端启动参数，服务端没有任何观测途径**。但它的**后果**被机制兜住了——声明小了只是 `wait` 变短，不会失败（第 2 条的 clamp）。

## 后果

**正面**

- B 档确认成立，阶段 2 可以按原架构推进，协议 §6 **不需要重写**（ADR 0004 的兜底分支没有被触发）
- 默认值 20s 在最差配置下也不会触发超时错误——**默认安全**
- `max_block_sec` 是「机制优于自然语言」的正例：客户端能力是**声明**的，越界由 server 收敛，不靠 agent 记住「别等太久」
- `wait` 超时返回即续租的设计被实测验证是无害的（超时后重连再 attach 即可）

**负面 / 代价**

- 20s 的默认值意味着**空闲成员每 20s 醒一次**。相比「挂 5 分钟」，轮询次数多 15 倍。每次 `wait` 都是一次 MCP 往返 + 一次模型 turn 边界，空转成本需要实测（列入阶段 2 未定项）
- 想把 `wait` 拉长到分钟级，必须**逐客户端改配置**。多 runtime 环境里这是一份需要维护的「接入清单」，且新 CLI 接入时容易漏
- `max_block_sec` 自报值可能与真实超时不符（客户端超时改了但声明没改，或反之）。server 只能 clamp，无法验证——**声明与实际不一致时，失败仍然发生在客户端**
- DSH 无进度续期，意味着 DSH 侧的 `wait` 天花板完全取决于 `toolCallTimeoutMs` 一个静态值

## 备选方案

| 方案 | 放弃理由 |
|---|---|
| `wait` 默认 300s，让客户端自己配 | 默认配置下**必然失败**，且失败信息（MCP timeout）会把责任指向空间服务。默认值必须在不改任何配置时可用 |
| 靠 progress 通知续期当主机制 | 只有 opencode 支持；DSH 连 `progressToken` 都不发。属各 CLI 私有实现细节，随时可变。**实测已证明不可依赖** |
| 不用 MCP，用内置 shell 工具阻塞（`sleep`） | 实测确实不受 30s 限制（两边 `sleep 150` 都通过），但它给不了返回值，也拿不到任务——只能当「闹钟」，还得再调一次 `wait`。且把空间语义塞进 shell 命令等于放弃跨 runtime 抽象 |
| 退回 A 档（纯拉取） | 丢失自动推进，需人反复催。ADR 0004 已论证只作兜底 |
| 让 server 主动推（长连接以外的 webhook） | 交互式 session 无稳定可达 URL，见 ADR 0004 备选方案 |

## 验证

本 ADR 的依据全部来自可复现探针：`probe/README.md`（如何跑）、`probe/RESULTS.md`（结论与证据）、`probe/results/raw/*.json`（原始记录）。

**未验证、且不得外推的**：`claude -p` / `codex exec` 本机未安装，其默认超时可能完全不同。**新接入一个 runtime，必须重跑 P3 两项（默认值撞墙 + 调高恢复），不得以本 ADR 的数值代替实测。**
