# 0004. 唤醒以 `wait` 长轮询为主路径

- **状态**：已接受（**待阶段 1 技术探针验证**）
- **日期**：2026-10-28
- **影响面**：接入层 / agent 的行为约定 / 无人值守能力

## 背景

中心服务有了（ADR 0001），一个任务派下去了，但**目标 agent 不会自己动**。怎么让它开始干活？

最先想到的是"唤醒它"。但这里有一个必须先纠正的目标定义：

> **agent 是"用户启动的一个 session"，不是常驻服务。**

交互式 CLI 的 turn 是**由输入事件驱动的**：没有人打字，就没有 turn，它不执行任何代码。因此服务中心**推不动**它。试图注入（往 stdin 写、用 tmux `send-keys`）**跨 runtime 完全不通用**，且依赖运行时的具体实现细节——属于 hack，不是机制。

所以正确的问题不是"怎么唤起它"，而是：

> **它在线的时候，怎么让它知道自己该干活？**

## 决策

**三档并存，共用同一套接口**：

| 档 | 机制 | 定位 |
|---|---|---|
| **B（主路径）** | agent 在自己的 turn 里调用 `wait(since, timeout)` 阻塞等待；有任务立刻返回，无任务超时返回 | 人在场、可干预 |
| **D（可选）** | supervisor 发现成员离线时，触发 headless 执行（`opencode run` / `claude -p` / `codex exec`） | 无人值守流水线 |
| **A（兜底）** | 纯拉取：启动时读收件箱，之后不主动；配合 IM 通知人 | runtime 不支持阻塞工具时 |

B 档的行为循环：

```
attach → loop[ wait → 有活则 claim/干活/publish/DONE → 无活则续租 → wait ]
```

设计要点：

1. `wait` 在服务端是**挂住连接**，不是 agent 侧高频轮询
2. `wait` 返回时**顺带续租 + 心跳**，一次调用做三件事，不会漏续租
3. **人打字就是打断**：人在会话里说一句话就是新 turn，挂着的 `wait` 作废（无害）。这就是"随时介入"，且**不需要任何额外机制**
4. 断线重连 = 再 `attach`，服务端补投未确认任务

## 后果

**正面**

- `wait` 只要求 runtime 能调用阻塞工具，**不要求任何 runtime 私有扩展**——兼容性远好于 hook 方案
- 顺带满足"人可中途干预"：交互式 session 天然可打断，而阻塞的工具调用正好让人有机会插话
- B 与 D 共用同一套协议，服务端不关心成员是人开的还是自己起的 → **人工调试与夜间无人值守不需要两套实现**
- 直接锚定"论坛"语义：**操作允许离线**，不是聊天室

**负面 / 代价**

- **阻塞调用可能被 runtime 硬超时打断**（工具超时或 turn 超时）。若成立，B 档失效、架构退回 A 档。**这是本 ADR 标"待验证"的唯一原因**
- agent 在 `wait` 期间占用一个活跃 session 与 token
- D 档意味着服务能起进程，是**高风险能力**：必须限制为 `supervisor` scope，并有并发上限与预算熔断
- 长连接的保活、超时、重连要正确处理，否则会出现"假在线"

## 备选方案

| 方案 | 放弃理由 |
|---|---|
| 用 hook 作为挂载点 | hook 是无状态事件回调，无法承载身份与租约；且**部分 runtime 完全没有项目级 hook**，兼容性差。hook 保留用于**围栏**（越权写拦截、会话结束释放租约），不做**大门** |
| 注入 stdin / tmux `send-keys` | 跨 runtime 不通用、脆弱、依赖实现细节 |
| A2A 的 push notification（webhook） | 要求对端有**可达 URL**，而交互式 session 没有。适合 D 档常驻服务，不适合 B 档 |
| 纯拉取（A 档）作为主路径 | 需要人每次都手动去问"有没有活"，失去自动推进；只能作兜底 |

## 验证要求（阶段 1）

本 ADR 的成立依赖三个外部事实，**必须以实测为准，不以文档为准**：

| # | 待验证 | 不成立的后果 |
|---|---|---|
| P1 | 目标 CLI 支持 headless 非交互执行 | D 档不存在 |
| P2 | 目标 CLI 能挂 MCP over stdio | 接入层重选 |
| **P3** | **单 turn 内调用阻塞工具不会被硬超时打断** | **B 档不成立 → 本 ADR 失效，架构退回 A 档，协议 §6 整体重写** |

注意 P3 有两个独立的超时来源要分别测：**工具调用超时** 与 **turn 超时**。

## 备注

**"能等人介入"与"能挂着等活"是同一件事的两面**——本质都是"这个 session 一直活着"。交互式 session 本来就活着，只要它愿意 `wait`，就不需要任何人去唤起它。这个认识是本 ADR 的核心。
