# 0002. 消息/状态/产物三分平面；状态由事件归约

- **状态**：已接受
- **日期**：2026-10-28
- **影响面**：协议 / 存储 / 接口形状 / 可观测性

## 背景

在确定"用中心服务"（ADR 0001）之后，紧接着的问题是：**中心服务里到底存什么、怎么存。**

一个容易的错法是「把所有东西都存成记录」——任务、消息、状态、产物引用，全放一张大表或一棵目录树。这样做的直接后果是两类问题：

1. **量的问题**：心跳、进度提醒、"我收到了"这类信号高频且转瞬即逝，与「当前进行到哪一步」这种低频但必须准确的事实，混在一起存会让存储被垃圾淹没。
2. **并发写的问题**：多个 agent 都可能想更新「进度」，如果都直接写同一个状态对象，就会互相覆盖。谁该写、谁不该写，需要一个不自相矛盾的答案。

另外还有一个与本项目核心痛点直接相关的诉求：**调试**。项目起因之一就是"子 agent 不好调试"，如果新架构里 agent 的行为仍然只能靠猜，那等于没解决。

## 决策

### 1. 三个平面分离

| 平面 | 内容 | 寿命 | 载体 |
|---|---|---|---|
| **控制面** | 任务、认领、租约、即时消息、presence | 秒～小时 | 服务内存 + 关系表；纯信号不归档 |
| **状态面** | 「谁做到哪一步」 | 长期，只要最新值 | 服务端，覆盖式 |
| **数据面** | 产物、大文件、handoff、报告 | 长期，要版本 | 文件系统 / git / NAS |

**跨平面的铁律：消息只传引用（URI + sha256 + size），不传内容。**

### 2. 状态由事件归约，agent 只发事件

```
agent ──append──▶ events（append-only，不可删改）
                       │
              server 归约（唯一写者）
                       ▼
              state（覆盖式，只存最新值）
```

- **单写者**：只有 server 能计算 state，并发覆盖问题从根上消失
- **trace 免费**：事件流本身就是调试记录
- **可重放**：state 算错时重放事件即可重算

## 后果

**正面**

- 单一写者消除了多个 agent 争抢"更新进度"的整类竞态
- 事件流直接产出调试 trace，**正面解决了项目最初的痛点**
- 数据量可控：高频信号不落盘，只有"必须被下一个人接着读"的东西才持久化
- 大文件问题被同一条铁律顺手解决：内容寻址后消息里只有引用
- 可审计：谁在什么时候改了什么，全在事件流里

**负面 / 代价**

- **归约逻辑可能变复杂**：状态不是直接写的，要写对「从事件算出状态」的规约函数
- **schema 演进成本**：事件是不可变的，旧事件格式要能被新代码读懂（需要版本化事件）
- **需要额外的清理策略**：控制面信号不归档，但也不能无限增长（TTL / 快照压缩）
- 人不能再用"看一眼 state.json"了解全貌 → 必须提供等价视图

## 备选方案

| 方案 | 放弃理由 |
|---|---|
| 直接写状态对象（无事件流） | 多 agent 并发写会互相覆盖；且没有 trace，调试问题没解决 |
| 全部落文件（每个事件一个文件） | 文件爆炸，且跨机文件系统语义不可靠（ADR 0001） |
| 全部走消息队列、状态只在内存 | 服务重启即失忆，无法恢复。**可恢复性是硬需求** |

## 备注

这个模式（写侧 append 事件、读侧归约出视图）在分布式系统里叫 CQRS / event sourcing，是成熟做法而非新发明。选它主要是因为它**同时解决并发写、可恢复、可观测三个问题**，而这三个都是本项目的硬需求。
