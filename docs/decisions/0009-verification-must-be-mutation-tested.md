# 0009. 验收必须做变异测试：全绿不等于完成

- **状态**：已接受
- **日期**：2026-10-28
- **影响面**：本仓的验收标准、所有后续阶段的「通过」判据
- **来源**：阶段 2 一次假绿灯

## 背景

阶段 2 原型第一次验收是 **25/25 全绿**，于是被标为「已完成」，并写进了 ROADMAP 与 CHANGELOG。随后 4 个独立 reviewer 做了 19 个源码变异（故意改坏实现，看测试是否变红）：

> **9/19 变异存活（≈53%）**。也就是说，把 R1、`verify`、租约回收、认领名额、`wait` 超时、`max_block_sec`、并发二次校验、scope —— 一个个删掉，测试依然打印「25/25 passed」。

最刺眼的一个是测试侧变异 **T1**：把「人插话」这一步整个删掉（连取消通知都不发），

```
-  A.cancelPending()
```

**依然 25/25。** 因为那两条断言测的是测试脚本自己的 `pending` Map：删掉本地条目 → Promise 不再 settle → `settled === false` 必然成立。它证明的是脚本能删 Map，不是系统能被打断。

同类问题：

| 现象 | 后果 |
|---|---|
| `check('A CLAIMED → WORKING', true)` 这类占位断言 | 即使迁移是空操作也 PASS |
| 只断言 `state === 'PENDING'` 而不试「能否再认领」 | 掩盖了 100% 命中的回收死锁 |
| `space_verify` 恒返回 `ok:true` 仍 25/25 | 「可重放对账」这条证据没有负向测试 |
| e2e 断言采信 agent 自己的 stdout | 证明的是「模型会照着剧本调工具」 |

## 决策

**把「断言必须有牙」变成硬性验收标准：**

1. **每条断言都必须能说出「哪个缺陷会让它变红」。** 写不出来就不算断言，改成 `TODO:` 留在注释里，不计入通过数。
2. **P0 级别的行为必须有变异测试**：提交前至少对每个 P0 敲一次「删掉这段实现 → 测试必须红」。
3. **关键结论回库核对，不采信任何一方自述**：测试脚本直接开 `sqlite` 查 `tasks` / `events` 行。
4. **对账器本身要有负向测试**：手工篡改投影 → `verify` 必须报 drift。
5. **测试必须能优雅失败**：断言之外的异常落成一条 `FAIL`，不能让脚本崩掉、丢掉前面的汇总。
6. **文档里的通过结论必须标证据强度**：「客观核对」/「旁证（自述）」/「未覆盖」三档，不许把旁证写成结论。

## 后果

**正面**

- 同一批变异里，存活率从 9/19 降到 2/13；存活的 2 个是**双重防护**（删掉一层，另一层仍然拦得住），不是漏洞；
- 修 bug 时立刻得到回归保护：这轮修的 `max_block_sec` 遮蔽 bug 就是新断言自己抓到的；
- 「阶段完成」从此有可复核的含义，而不是一个通过率数字。

**负面 / 代价**

- 写测试变慢：一个有牙的断言通常要先想清楚「怎么让它失败」；
- 验收脚本变长（55 条），跑一次约 40 秒；
- 变异测试目前靠人工/tmp 脚本，没有进 CI。**这是明确的欠债**：应该在阶段 3 之前把 `npm run mutate` 做出来，否则「有牙」会随时间腐化；
- 双重防护会让变异测试出现「存活」的假信号，需要人工判读——这是变异测试本身的固有噪音。

## 备选方案

| 方案 | 放弃理由 |
|---|---|
| 提高覆盖率阈值 | 覆盖率与「能否发现缺陷」几乎正交；这次全绿的代码覆盖率并不低 |
| 只靠 review | 这次正是 review 抓到的；但 review 不可回归、不可自动化，只能补不能替 |
| 追求 100% 变异杀死 | 双重防护与等价变异会让 100% 无意义，且成本极高。目标定在「P0 必须被杀」 |
| 把断言写成快照测试 | 快照只能发现「变了」，不能发现「坏了」；本项目的缺陷大多是「没变但还是坏的」 |
