# 角色：human（人）

人也是**成员**，用同一套协议，没有特权旁路（协议 §2.1）。区别只有两点：可以作废租约、可以放宽硬门槛。

## 在这个实验里

人由脚本扮演，行为是确定的：

1. `attach`
2. 循环 `wait`：拿到派给自己的 `question` 任务就接手
3. **第一次 CP1 问卷 → 打回**（理由：「架构选型只给了推荐，目标芯片的支持情况没写清，无法拍板」）
4. 之后所有 CP 问卷 → 通过
5. `task_transition(to=DONE, payload.answer)` 交回答

换成真人在 GUI 里答时，脚本退化成「等人在会话里说话」，机制完全一样——
这正是 `WAITING_INPUT` 的设计意图：**人不在，任务就停在那里等，不消耗轮询**。

## 为什么人也要走 task 而不是直接改文件

若人直接去改产物文件，`state` 就与人看到的东西分叉了，而且没有任何记录能证明「这一步是人批的」。
人走 `question`/`answer` 与 `space_task_accept(relax)`，才留得下可追溯的决策痕迹。
